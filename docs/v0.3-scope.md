## 2. Per-gap adjudication

### 2.1 Custom project-level agent-gate registration

**Verdict.** `already-handled`.

**Evidence.** `src/claude_plan_execute/gates/invariants.py:52-91` defines `InvariantEntry` with `kind: Literal["shell", "agent"]`, `prompt_template`, `model`, `effort`, `parallel_safe`, `on_failure`, `when`, `comment`. `compile_entry` (lines 97-163) compiles a `kind: agent` entry into `Gate(kind="agent", prompt_template=..., model=..., effort=..., ...)` indistinguishable from the built-in agent gates. `register_invariants_on` (lines 252-278) registers each `(name, Gate)` pair on `default_registry()`. The runner's Phase 4 dispatch (`runner.py:319-380`) resolves gate names against the same registry. A project can register a domain-flow validator today by adding to `docs/invariants.yaml`:

```yaml
- name: cluster-permissions-validator
  kind: agent
  prompt_template: docs/agents/cluster-permissions.md
  model: opus
  effort: max
  parallel_safe: true
  on_failure: block
  when: ["task_class:cluster"]
```

…and listing it in `defaults.gates: [..., cluster-permissions-validator]`.

**Rationale.** The owner's hypothesis ("a project cannot register a new named agent gate without editing the build tool's source") is empirically false. The capability exists; its surface is named `invariants.yaml` rather than `tasks.yaml.custom_gates`, which is the discoverability problem.

**Pushback.** Adding a parallel `defaults.custom_gates: { name: { kind, prompt_template, ... } }` field in `tasks.yaml` would be a second mechanism for the same primitive. That's anti-DRY. Two surfaces drift; users get confused about which to use.

**What ships in v0.3.** Doc-only. Rename the conceptual title in README and migration docs from "invariants" to "custom gates / invariants" — make the dual purpose explicit. Add a recipe in the docs showing project-level agent-gate registration. The file path stays `docs/invariants.yaml` (governed by `defaults.invariants_file`) — no source change. If a future v0.4 wants to add an `invariants_file` alias for clarity, that's a code change for that release.

**General-purpose check.** The mechanism already passes — `invariants.yaml` knows nothing about citations, ACL, RTL.

**Effort.** S (docs only).

### 2.2 Metric-threshold gate primitive

**Verdict.** `gap-refuted`.

**Evidence.** `src/claude_plan_execute/gates/shell.py:43-83` runs an arbitrary command and treats `proc.returncode == 0` as PASS. A coverage threshold like "≥ 80%" is one shell command:

```yaml
defaults:
  gates: [tests, coverage]

# in invariants.yaml:
- name: coverage
  kind: shell
  command: "pytest --cov && coverage report --fail-under=80"
  on_failure: block
```

The exit code is the threshold check.

**Rationale.** The user's hypothesis confuses two concepts. (a) "Pass when value ≥ N" is a **shell predicate** — already supported. (b) "Track value over time, alert on regression" is a **metric history** — a different problem requiring a time-series store, dashboard graphs, and aggregation. Conflating them produces a YAML primitive that's a thin wrapper over (a) and doesn't deliver (b).

**Pushback.** Shipping a `metric_threshold:` schema entry would be a second way to express what `bash -c` already expresses, with no observability gain. The metric-history concern is a dashboard problem (§2.14).

**What ships in v0.3.** Nothing. Document the existing `bash -c` pattern as the canonical way to express thresholds.

**General-purpose check.** N/A.

**Effort.** Zero.

### 2.3 Declarative dev-server lifecycle

**Verdict.** `gap-confirmed`. **Highest-priority of all confirmed gaps.**

**Evidence.** `src/claude_plan_execute/gates/templates/design-fidelity.md:11-13` reads:

> "The project is responsible for starting the dev server before the gate runs. If the URL above is unreachable, emit `VERDICT: FAIL`…"

This punts the problem to the operator. For an unattended 50-task run that includes ~10 UI tasks each requiring a Playwright-driven gate, the operator must keep `npm run dev` alive in another terminal for the entire run. If it dies, every UI task fails downstream.

There is no `services:`, `setup:`, `before_gate:` block anywhere in the schema (`schema.py:46-71`). The runner has no concept of lifecycle for processes outside the `claude` subprocess.

**Rationale.** Real gap. Bayān explicitly needs this for design-fidelity. Almost every modern web project needs it for any browser-driven check. The build tool is the natural place to own service lifecycle because it owns task scheduling.

**Design (paste-ready).**

Add `services:` as a top-level key in `tasks.yaml`:

```yaml
services:
  - name: dev-server
    command: "npm run dev"
    cwd: "frontend"                         # optional, default ".".
    env:                                    # optional
      VITE_DEV_PORT: "5173"
      DATABASE_URL: "postgresql://localhost/bayan_dev"
    ready_check:
      kind: http                            # http | tcp | shell
      url: "http://localhost:5173"          # for kind=http
      # OR: port: 5173                      # for kind=tcp
      # OR: command: "curl -fs http://localhost:5173"  # for kind=shell
    ready_timeout_seconds: 60
    lifetime: run                           # run | phase | task | gate
    log_file: ".cpe/services/dev-server.log"
    depends_on: []                          # other service names

  - name: postgres
    command: "docker compose up postgres"
    ready_check: { kind: tcp, port: 5432 }
    ready_timeout_seconds: 30
    lifetime: run

  - name: minio
    command: "docker compose up minio"
    ready_check: { kind: http, url: "http://localhost:9000/minio/health/ready" }
    lifetime: run
```

Per-task / per-phase / per-gate scoping. To match the existing `gates`/`gates_extra` overlay convention, the project-wide list is `services_required` and each higher layer overlays via `services_required_extra` (additive, not override):

```yaml
defaults:
  services_required: [postgres, minio, dev-server]

phases:
  - id: ui-shell
    defaults:
      task_class: ui
      services_required_extra: [storybook]        # ADDS storybook to ui-shell tasks

tasks:
  - id: 17
    services_required_extra: [redis]              # ADDS redis just for task 17
```

The runner unions these in the same order it unions `gates` + `phase.gates_extra` + `task.gates_extra`: `defaults.services_required ∪ phase.services_required_extra ∪ task.services_required_extra`. There is no "remove" semantics — if you want a task to NOT need postgres, restructure your defaults. Override-vs-add ambiguity is a debugging tax we don't want.

Gates can also declare requirements in their `Gate` registration. The `design-fidelity` factory already takes `dev_server_url`; v0.3 adds an implicit `services_required: [<server-named-by-url>]` based on the resolved URL — or the project lists it explicitly. **Explicit is preferred.** Update the factory to accept `services_required: list[str] | None`.

**Schema additions.** New top-level field `services: list[ServiceSpec]` in `TasksFile`. New optional `services_required: list[str]` in `Defaults`. New optional `services_required_extra: list[str]` in `Task`. (`Phase.defaults` is a loose dict, so phase-level `services_required_extra` works without further schema work — same convention as `gates_extra`.) New `ServiceSpec` Pydantic model:

```python
class ReadyCheck(BaseModel):
    model_config = ConfigDict(extra="forbid")
    kind: Literal["http", "tcp", "shell"]
    url: str | None = None
    port: int | None = None
    command: str | None = None

class ServiceSpec(BaseModel):
    model_config = ConfigDict(extra="forbid")
    name: str
    command: str
    cwd: str | None = None
    env: dict[str, str] = Field(default_factory=dict)
    ready_check: ReadyCheck
    ready_timeout_seconds: int = 60
    lifetime: Literal["run", "phase", "task", "gate"] = "run"
    log_file: str | None = None
    depends_on: list[str] = Field(default_factory=list)
```

**Module additions.** `src/claude_plan_execute/services.py`:
- `ServiceManager` class: holds running `subprocess.Popen` handles by service name.
- `start(name) -> None`: spawn process, run ready check with timeout. Raises on failure.
- `stop(name) -> None`: SIGTERM, then SIGKILL after grace.
- `ensure(required: list[str]) -> None`: bring up listed services not already running.
- `tear_down_for_scope(scope: str)`: stop services whose `lifetime` matches the scope.
- Service-startup failures emit a `service_unavailable` FailureRecord and block dependent tasks/gates.

Ready-check implementations:
- `http`: GET the URL, accept 2xx/3xx within `ready_timeout_seconds`. Retry every 1s.
- `tcp`: open a socket to `(host or 127.0.0.1, port)`, accept connect within timeout.
- `shell`: run command, accept exit 0 within timeout.

**Runner integration.** In `cli.main()`, after loading the tasks file, instantiate `ServiceManager`. Before the task loop, `manager.ensure(<services required by ANY task with lifetime=run>)`. Inside `execute_task`, before Phase 4 (gates), `manager.ensure(<gate-scoped services>)`. After each task / phase / run, `manager.tear_down_for_scope(...)`.

**Dashboard.** Add `/api/services` endpoint listing services, status, and last 200 lines of log. New panel in dashboard. Restart button per service.

**Failure semantics.** A service that crashes mid-run produces a `service_crashed` FailureRecord; the runner attempts `start()` once before re-running the task that needs it. After 3 consecutive service crashes the runner blocks the task with reason `service_unstable`.

**Decisions made inline.**
- *Why a separate `services:` block, not `pre_gate_command:` per gate?* Because services have lifetime longer than a gate; rebooting the dev server on every UI task adds 5+ seconds of cold start ×10 tasks = 50s wasted, and risks a stale state mid-run. Separate lifecycle.
- *Why `lifetime: run` as default and not `task`?* Most projects' dev servers start once and stay up. `task` lifetime is for services that mutate state per-task (rare).
- *Why no `health_check` separate from `ready_check`?* YAGNI for v0.3. Add `health_check` only if a real project needs it.

**General-purpose check.** ServiceSpec knows nothing about Bayān. The same primitive serves a Rails app, a Django backend, a Go service, etc. The "dev server" in design-fidelity stays a generic URL; `services` populate the URL's backing process.

**Migration notes.** Existing v0.2.0 task files have no `services:` and no `services_required:`. They continue to work with no service management. Projects opt in by adding the block.

**Effort.** **M** (1.5–2 weeks). Service lifecycle has more edge cases than it first looks: zombie processes, port conflicts, stdout/stderr piping, signal forwarding to subprocess groups, cross-platform process-group handling (`os.setsid` on Linux/Mac, different on Windows but Bayān is Linux/Mac so we punt that).

### 2.4 Manual-checkpoint task type

**Verdict.** `gap-confirmed`, but reshape it as a **gate kind, not a task kind**.

**Evidence.** `src/claude_plan_execute/schema.py:84-107` — Task model has no `kind` field. All tasks run Plan → Review → Implement → Gates uniformly. The state machine in `state.py:21-24` knows statuses (planning, reviewing, …, blocked, done) but no "awaiting_human" status.

**Rationale.** Real gap. Bayān has phase boundaries where the operator wants to eyeball outputs before continuing — e.g., after phase E (synthesis) but before phase F (cluster retrieval) lands code that depends on synthesis correctness. The operator wants a single human-decision point, not 50 of them.

**Pushback (gentle).** The owner proposed a `kind: manual` task. I'd argue a **`kind: human` Gate** is more composable:

- Tasks are units of plan/review/implement. A "manual" task with no plan/review/implement is structurally awkward — what does `--skip-to plan` do?
- A human gate fits the existing model: post-implement validation. If the user wants a checkpoint AFTER task 25 completes, they declare `gates: [tests, lint, human-checkpoint]` on task 25.
- For phase-end checkpoints, a phase-overlay `gates_extra: [human-checkpoint-end]` works.

**Design.**

New gate kind. **Two Literal extensions are required**, not one:

1. `Gate.kind` in `gates/__init__.py:40` — extend to `Literal["shell", "agent", "human"]`.
2. `InvariantEntry.kind` in `gates/invariants.py:57` — same extension. Without this, project-supplied YAML registrations of human gates fail Pydantic validation at load time.
3. `compile_entry` in `gates/invariants.py:97-163` — add a `human` branch that produces a `Gate(kind="human", prompt_template=entry.prompt_template, sentinel_path=..., ...)`. The validator in `_check_shell_specifiers` should be relaxed (or split) so human entries are accepted with only `prompt_template` and don't trip the shell-specifier guard.

```python
@dataclass(frozen=True)
class Gate:
    kind: Literal["shell", "agent", "human"]
    # ... existing fields ...
    sentinel_path: str | None = None       # NEW: file to wait on (default plans/task-<id>/gates/<name>.approval)
    timeout_minutes: int = 1440            # 24h default reasonable for human gates; ShellGate / AgentGate keep their own 10m default via factory args
```

**Reuse `prompt_template`, do NOT add a new `prompt` field.** The existing `prompt_template` in Gate (`gates/__init__.py:43`) already has dual path/inline semantics: `AgentGate._load_template` (`gates/agent.py:19-39`) reads it as a file if it exists, otherwise verbatim. `HumanGate` uses the exact same loader for the request body — one field, two consumers, no drift.

`HumanGate` runner in `gates/human.py`:
- Writes a markdown prompt to `task_dir/gates/<name>.request.md` describing what to review and how to approve/reject.
- Polls for `task_dir/gates/<name>.approval` or `task_dir/gates/<name>.rejection`.
- Approval file content is captured into `GateResult.output`.
- Times out per `timeout_minutes` (default 24h). Produces a `human_gate_timeout` FailureRecord on timeout.

Two ways to approve:
1. **CLI / file-based**: operator runs `claude-plan-execute approve TASK_ID GATE_NAME --note "looks good"`. Touches the sentinel file.
2. **Dashboard**: Approve / Reject buttons in the gate-results panel call `POST /api/gates/<task_id>/<name>/decision` with `{decision: "approve|reject", note: "..."}`.

**Schema additions.** None to `tasks.yaml` (gate registration goes through `invariants.yaml` or built-ins). Adding a `human-checkpoint` built-in:

```yaml
# in invariants.yaml — or as a built-in factory in gates/builtin.py
- name: human-checkpoint-end
  kind: human
  prompt: |
    The phase has completed. Review:
      - {plans_dir}/task-{id}/gates/security-auditor.txt
      - {plans_dir}/task-{id}/gates/design-fidelity.txt
    Approve to continue. Reject (with a note) to block the next task.
  timeout_minutes: 720
  on_failure: block
  parallel_safe: false
  when: ["always"]
```

**Runner integration.** `_run_one` in `gates/__init__.py:176` already dispatches by `kind`. Add the `human` branch:

```python
if gate.kind == "human":
    return HumanGate(name=name, gate=gate, task=task, task_dir=task_dir).run()
```

When a human gate is running, the runner sets `state.set_status(tid, "awaiting_human", gate=name)` so the dashboard surfaces a clear "waiting on you" state.

**Decisions made inline.**
- *Why polling, not a callback / webhook?* Simpler. Sentinel files are zero-infrastructure and survive process restarts. The dashboard wraps the touch-file with a button.
- *Why default timeout 24h?* Long enough for an overnight wait. Configurable per-gate.
- *Why parallel_safe=false?* Human attention is a serial resource — interleaving prompts confuses operators.

**General-purpose check.** No domain coupling.

**Effort.** **M** (1 week). Polling + sentinel + dashboard wiring + state machine extension.

### 2.5 Parallel task execution for independent tasks

**Verdict.** `gap-confirmed`. (Originally recommended for v0.4 deferral; owner directive overrides — ships in v0.3 with `branch_per_task` as a schema-level prerequisite. See build-order item 12.)

**Evidence.** `src/claude_plan_execute/cli.py:246-256`:

```python
for task in ordered_tasks:
    s = state.get(task["id"])["status"]
    if s == "done":
        ...
    execute_task(...)
```

Strict serial. Even with no `depends_on`, two independent tasks run back-to-back.

**Rationale.** Real wall-clock cost on a 50-task slate. Phase G (UX shell) has multiple tasks that don't share `key_files` (font integration, public KB discovery surface, settings shell, mobile responsive shell). They could run together.

**Pushback against shipping in v0.3.** The thing that makes parallel-tasks safe is **branch-per-task** (§2.12). Without it, two parallel implements race on `git commit` against the same branch, and the loser must rebase or lose work. Building parallel-task scheduling on top of single-branch commits is a bug factory.

Service contention is the second blocker: two tasks each spinning up their own `npm run dev` collide on port 5173 unless the runner allocates ports dynamically. That requires `services:` to support templated ports — extra design surface.

Rate-limit contention is the third: parallelism multiplies the rate at which you hit Anthropic's API caps. Without §2.15 rate-limit retry, parallel runs fail faster than serial.

So the build order is rate-limit → branch-per-task → services → THEN parallel-tasks. By that point we'll know whether the wall-clock saving is worth the scheduler complexity. My bet is it isn't, for a 50-task slate that runs over a weekend regardless. Most slates would benefit more from a `--continue-from FAILED` flag than from concurrency.

**Design (sketch only — not for v0.3).**
- `defaults.parallelism: int` knob (default 1).
- Scheduler in `runner.py` uses `concurrent.futures.ThreadPoolExecutor` with `parallelism` workers. Each worker calls `execute_task` for one task.
- Eligibility: a task is eligible when all `depends_on` tasks have `status == "done"` AND no in-flight task shares any path in `key_files` (conservative; configurable).
- Each task runs on its own branch (§2.12) and merges back via PR.
- Dashboard shows N concurrent task panels, each with its own log stream.

**Decisions made inline.**
- *Why not ship "easy parallelism" now (just two tasks at a time, share a branch)?* Because the easy version creates rebase conflicts that require human intervention — exactly the autonomy regression we're trying to avoid. A parallel scheduler that needs babysitting is worse than serial.

**General-purpose check.** Schedulers are domain-agnostic; they show up only at the orchestration layer.

**Effort.** L (3 weeks) including UI restructuring, scheduler tests, contention resolution. Defer.

### 2.6 Gate-to-gate ordering

**Verdict.** `gap-refuted`.

**Evidence.** `src/claude_plan_execute/gates/__init__.py:253-273` already partitions:

```python
serial = [(n, g) for (n, g) in runnable if not g.parallel_safe]
parallel = [(n, g) for (n, g) in runnable if g.parallel_safe]

# Serial first ...
# Then parallel.
```

`parallel_safe: false` gives explicit "before everything else" ordering. The only ordering need that survives in practice is "this gate uses the dev server exclusively, run it serially" — handled.

**Rationale.** The owner's example (lint before design-fidelity) is logically backwards: lint and design-fidelity test orthogonal contracts. A typecheck failure has no bearing on whether the app's mobile menu hides the hamburger correctly — the design-fidelity gate exercises the running app, not the source. They run in parallel, both fail or pass independently, and we get more signal per task.

The plausible "tests should run before security-auditor" ordering is also wrong on inspection. Security-auditor reads the diff, not the running tests. Two failures in parallel give the implementer two distinct fix points.

The genuinely-blocking ordering ("must finish before next") is `parallel_safe: false`. Everything else is fan-out.

**Pushback.** Shipping a gate DAG would be 200+ lines of scheduling code for marginal value. The savings (don't run gate B after A fails) are eaten by the cost of correctness bugs in the DAG resolver. **No.**

**What ships in v0.3.** Nothing.

**General-purpose check.** N/A.

**Effort.** Zero.

### 2.7 Per-gate cost / budget cap

**Verdict.** `partially-handled`. Wall-clock yes, tokens no. Ship observability only.

**Evidence.** `Gate.timeout_minutes` (`gates/__init__.py:46`) gives per-gate wall-clock budget; ShellGate (`gates/shell.py:58`) and AgentGate (`gates/agent.py:75`) both honor it. Token usage: `claude.py:128-145` parses the JSON event for `result_text` and sets `_last_run_subtype`, but **discards `usage`**. No token counter, no budget tracking, no per-task or per-gate cost rollup.

**Rationale.** Real concern on a 50-task autonomous slate. Each task with 4 agent gates costs roughly: (plan + 3 review rounds + revise×2 + implement + 4 agent gates) = ~10 Opus invocations per task × 50 tasks = 500 sustained Opus runs. Cost-per-run varies wildly by codebase size and turn count.

**Pushback against shipping hard caps in v0.3.** Hard caps without observability is shooting in the dark — what's "too much" until you've seen the distribution? Observability first; tighten with data.

**Design (observability only).**

Capture token usage in `claude.py`:

```python
# in claude.py, after parsing the JSON result event:
usage = result_event.get("usage", {})
_last_run_input_tokens = usage.get("input_tokens", 0)
_last_run_output_tokens = usage.get("output_tokens", 0)
_last_run_cache_read_tokens = usage.get("cache_read_input_tokens", 0)
_last_run_cache_creation_tokens = usage.get("cache_creation_input_tokens", 0)
```

Each `run_claude` call writes a row to `task_dir/usage.jsonl`:

```json
{"timestamp": "...", "phase": "implement", "model": "opus", "input": 120000, "output": 8000, "cache_read": 95000, "cache_create": 5000, "duration_seconds": 220}
```

Phase 4 gate runners append their own rows with `phase: "gate:<name>"`.

Runner sums on `state.set_status(tid, "done")`:

```json
"task_id": "17",
"usage_summary": {
  "total_input_tokens": 1200000,
  "total_output_tokens": 80000,
  "total_cache_read": 950000,
  "total_runs": 8,
  "duration_seconds": 1840
}
```

Dashboard adds a **Cost** panel: per-task and per-phase rollups, with model breakdowns.

**Schema additions.** None.

**Decisions made inline.**
- *Why not enforce caps?* Premature. We don't know what's normal yet. After the Bayān run produces real numbers, v0.4 can ship `caps.max_input_tokens_per_task: 2000000` based on the p95.
- *Why JSONL not JSON?* Append-only writes survive interruption.

**General-purpose check.** No domain coupling.

**Effort.** **S** (3 days). Side-channel additions to `claude.py`, sum logic in `runner.py`, dashboard panel.

### 2.8 Multi-component projects (test_command list)

**Verdict.** `already-handled` via custom shell gates.

**Evidence.** A project with backend + frontend + worker can register multiple shell gates in `invariants.yaml`:

```yaml
- name: tests-backend
  kind: shell
  command: "pytest -q"
- name: tests-frontend
  kind: shell
  command: "npm test --prefix frontend"
- name: tests-worker
  kind: shell
  command: "go test ./..."
```

…and list them: `defaults.gates: [tests-backend, tests-frontend, tests-worker]`.

### 2.11 Long-context-fill continuation

**Verdict.** `partially-handled`. Ship a lightweight prompt convention.

**Evidence.** `src/claude_plan_execute/runner.py:296-311`:

```python
if claude._last_run_subtype == "error_max_turns":
    state.set_status(tid, "blocked", block_reason="implementer_max_turns")
    state.record_failure(tid, make_failure_record(
        failure_class="implementer_max_turns",
        phase="implement",
        ...
    ))
```

The task is marked `blocked`. The next run (re-attempt) would re-execute Plan → Review → Implement from scratch — the previous implement's progress is whatever happened to be committed to git, but no structured "resume from here" mechanism exists. The failure-context section in `prompts.py:181-212` injects prior-attempt summaries into the next attempt's plan and implement prompts, but those summaries don't contain "we got 60% through file X."

For Bayān's larger UI tasks (e.g., #38 KB CRUD UI = three screens, ~2000 lines of frontend code), exhausting `max_implement_turns: 200` on a single pass is plausible.

**Rationale.** Real gap, but the autonomous resume in the form the owner describes ("commit WIP, mark `[~]`, end session, next session resumes") is a brittle convention that depends on the model emitting WIP commits faithfully. We can ship a useful approximation cheaply.

**Design (S-effort prompt-convention version).**

Modify `prompts.build_implement_prompt` to instruct:

> 1. Implement in commit-sized chunks. After each logically complete chunk, run `git add -A && git commit -m "task-{id} WIP: <chunk-description>"`. Continue to the next chunk.
> 2. Maintain `plans/task-{id}/progress.md` with a checklist of items from the plan. Mark items `[x]` when done, `[~]` when in progress, `[ ]` when not started.
> 3. If you sense you may run out of turns, commit the current chunk, update progress.md, and finish.

On the next attempt, `runner.execute_task` checks for `task_dir/progress.md`. If it exists and has any `[~]` or `[ ]` items, it sets `_resume_mode = True` and routes to a different prompt builder, `build_resume_prompt`:

```python
def build_resume_prompt(task, plan_path, progress_path, commit_message, *, persona="", failure_context=""):
    return failure_context + persona + (
        f"You are resuming an in-progress implementation.\n\n"
        f"TASK {task['id']}: {task['title']}\n\n"
        f"Read the validated plan at: {plan_path}\n"
        f"Read the current progress at: {progress_path}\n"
        f"Items marked [x] are done. Items marked [~] or [ ] are not.\n\n"
        f"Continue from the next [~] or [ ] item. Update progress.md as you go.\n"
        f"Commit on completion with message:\n   {commit_message}\n"
    )
```

Skip Plan phase entirely on resume (`skip_to="implement"` semantics, automatic).

**Decisions made inline.**
- *Why progress.md and not parsing git log?* Git log is unstructured. progress.md gives the implementer a checklist it owns and reads.
- *Why not split the implement phase into N chunks the runner controls?* Far larger change; defer. The convention version is 90% of the value at 10% of the cost.
- *What if the implementer doesn't follow the convention?* Same failure mode as today — task fails with `implementer_max_turns` and re-attempts from scratch. No regression.
- *Resume on a dirty tree.* `build_resume_prompt` runs `git status --porcelain` and surfaces uncommitted hunks to the implementer in the prompt body. The implementer is told to either commit them as the next chunk or revert them with explanation. Without this, resume can clobber unfinished edits the previous attempt left behind.

**Schema additions.** None.

**General-purpose check.** No domain coupling.

**Effort.** **S** (3 days). Two prompt builders, one resume detector, one test fixture.

### 2.12 Per-task branches / preview environments

**Verdict.** `gap-confirmed`. Build it.

**Evidence.** `src/claude_plan_execute/prompts.py:261-275` instructs the implementer:

```
3. Commit with message:
   {commit_message}
```

No branch instruction. Tasks land on whatever branch was checked out at run start. For 50 tasks, that's 50 commits in a row on `main` (or a feature branch) before the operator can review.

**Rationale.** Real gap, high-value. Branch-per-task gives:
- Per-task review surface (PR) the operator can read incrementally.
- Safe rollback: bad task = `git branch -D task/17-foo`, no rebase.
- Compose with parallel-task scheduling later (§2.5).
- Compose with auto-merge once gates pass.

**Design.**

New `tasks.yaml` defaults:

```yaml
defaults:
  branch_per_task: true                     # default false (backward-compat)
  base_branch: main                         # default main
  task_branch_template: "task/{id}-{slug}"  # default
  auto_pr: true                             # default false
  auto_merge: false                         # default false
  pr_body_template: "docs/pr-template.md"   # optional; default a built-in
```

**Slug.** `slug(task['title'])` lowercases, replaces non-alphanumeric with `-`, collapses repeats. `task/17-feat-kb-crud-ui`.

**Runner integration.**

In `execute_task`, before Phase 1 (plan):

```python
if branch_per_task:
    branch = task_branch_template.format(id=tid, slug=_slug(task['title']))
    # Create branch from base, idempotent.
    subprocess.run(["git", "fetch", "origin", base_branch], check=True)
    # If branch exists locally, check it out; else create.
    rc = subprocess.run(["git", "rev-parse", "--verify", branch], capture_output=True).returncode
    if rc == 0:
        subprocess.run(["git", "checkout", branch], check=True)
    else:
        subprocess.run(["git", "checkout", "-b", branch, f"origin/{base_branch}"], check=True)
```

After Phase 4 (gates) succeed:

```python
if auto_pr:
    # Push, idempotently.
    subprocess.run(["git", "push", "-u", "origin", branch], check=True)
    # Open PR if not already open.
    pr_body = render_pr_body(task, gate_results, plan_path)
    subprocess.run([
        "gh", "pr", "create", "--base", base_branch,
        "--title", task['title'], "--body", pr_body, "--draft", "false"
    ], check=False)  # tolerates already-open PR
if auto_merge:
    # Wait for CI, then merge.
    subprocess.run(["gh", "pr", "merge", "--auto", "--squash"], check=True)
```

**Schema additions.** Five new optional `Defaults` fields above. Per-task / per-phase override via existing layer mechanism.

**State.** Per-task entry gains `branch: str` and `pr_url: str | None`. `state.set_status(tid, "implementing", branch=branch)`.

**Failure handling.** A failed task on its own branch stays on that branch, blocked. Re-attempts continue on the same branch (additional commits pile up). Operator can `git branch -D` to abandon.

**Dependencies.** When task B has `depends_on: [A]`, B's branch is created from A's branch (NOT from `base_branch`). This carries A's commits forward. After A merges, B can rebase onto base. The runner doesn't auto-rebase — the operator merges in dependency order.

**Decisions made inline.**
- *Why default `branch_per_task: false`?* Backward compat. Existing v0.2.0 users keep their behavior; new projects opt in.
- *Why `auto_merge: false` by default?* Operator visibility on the first run. Once trust builds, flip on.
- *Why `gh` CLI, not GitHub API directly?* `gh` already authenticated, idempotent on PR creation, handles edge cases. Project must have `gh` installed; document this requirement.
- *What if the project uses GitLab / Gitea / Forgejo?* v0.3 is GitHub-only via `gh`. Add adapters in v0.4 if asked.
- *Mid-run merge race.* If the operator merges task A's PR while task B (which `depends_on: [A]`) is still in flight on its branch, B's branch loses the parent it was created from and may produce a degenerate PR. v0.3 documents operator hygiene: do not merge a parent task's PR while a dependent task is in flight; wait for the slate to complete (or for that dependency chain). The dashboard surfaces in-flight branches so the operator can see what to leave alone. v0.4 may add `gh pr merge --auto` interlocks to refuse merge while dependents are running.

**General-purpose check.** Branching and PR creation are domain-agnostic.

**Effort.** **M** (1.5 weeks). The git interactions are mostly straightforward; the dependent-branch chaining and auto-merge wait need real test coverage.

### 2.15 Claude-API rate-limit / backoff for unattended runs

**Verdict.** `partially-handled`. Build the wrapper.

**Evidence.** The Claude CLI does retry internally on 429s — when `Retry-After` headers are honored. But on extended rate-limit (Anthropic's daily / sustained-Opus caps), the CLI eventually exits with non-zero. `src/claude_plan_execute/claude.py:113-117`:

```python
if returncode != 0 and stderr:
    print(yellow(f"  stderr: {stderr[:300]}"))
```

…just prints and returns. No outer retry. The runner sees `code != 0`, the plan/review/implement output is missing, and the task aborts — silently for the gates phase, with the existing `error_max_turns` handling for implement. Neither path re-tries on rate-limit.

**Rationale.** Real gap. A 50-task autonomous run spanning hours WILL hit rate caps at some point. Without retry, that one moment failures the task; with retry, it pauses and continues.

**Design.**

In `claude.py`, detect rate-limit signals from stderr:

```python
_RATE_LIMIT_PATTERNS = (
    "rate_limit_error", "429",
    "Anthropic API rate limit",
    "Retry-After",
)

def _is_rate_limited(stderr: str) -> bool:
    return any(p.lower() in stderr.lower() for p in _RATE_LIMIT_PATTERNS)
```

Wrap `run_claude` body in a retry loop:

```python
def run_claude(prompt, *, model, effort, max_turns, timeout_minutes, skip_permissions, verbose,
               max_retries: int = 3, base_backoff_seconds: int = 60) -> tuple[int, str]:
    last_code, last_text = 1, ""
    for attempt in range(1, max_retries + 1):
        last_code, last_text = _run_claude_once(...)
        if last_code == 0:
            return last_code, last_text
        if not _is_rate_limited(_last_stderr):
            return last_code, last_text
        if attempt < max_retries:
            wait = base_backoff_seconds * (2 ** (attempt - 1))
            print(yellow(f"  Rate-limited; waiting {wait}s before retry {attempt+1}/{max_retries}"))
            time.sleep(wait)
    return last_code, last_text
```

Add a `rate_limited` failure_class to `state.FAILURE_CLASSES` for runner to record when retries exhaust.

**Schema additions.** Two optional cap fields:

```yaml
defaults:
  caps:
    max_rate_limit_retries: 3                # default 3
    rate_limit_base_backoff_seconds: 60      # default 60
```

**Decisions made inline.**
- *Why exponential backoff base 60s?* Anthropic's typical Retry-After is ~30s for short bursts. 60→120→240 gives 7 minutes of total wait, which spans most short rate windows.
- *Why not honor `Retry-After` from stderr?* Could be added later as a refinement; for v0.3, fixed exponential is simple and good enough.
- *Why a separate `rate_limited` failure class, not `implementer_timeout`?* Different cause, different remediation. Rate-limit is environmental and self-resolving over time; timeout is the model not finishing. The dashboard should surface them differently.

**Module changes.**
- `claude.py:55-146` wraps in retry loop.
- `state.py:30-38` adds `"rate_limited"` to `FAILURE_CLASSES`.
- `runner.py` updates failure-record creation paths to use `rate_limited` when `_last_run_was_rate_limited`.

**General-purpose check.** Rate-limit handling is domain-agnostic.

**Effort.** **S** (3 days).

### 2.16 `touches:<glob>` `when` matcher (new)

**Verdict.** `gap-confirmed`. The infrastructure expects this matcher; the runner doesn't yet implement it.

**Evidence.** `src/claude_plan_execute/gates/__init__.py:140-169` is `_when_matches`. The comment at line 153 explicitly notes:

```python
# Future tasks add cases here:
#   - "touches:<glob>"     (enhancement plan §2.1)
```

Only `always` and `task_class:<name>` are implemented. The `touches:<glob>` matcher would compare against `task['key_files']` so a project can declare:

```yaml
gates:
  - name: security-auditor
    when: ["touches:**/auth/**", "touches:**/permissions/**", "touches:**/acl/**"]
```

…and have the gate run only on tasks whose `key_files` includes paths matching any glob.

**Rationale.** With 50 tasks of varied surface area, blanket `gates: [security-auditor]` runs the agent on every task even when nothing security-relevant changed. Tokens add up. Project wants targeted runs.

**Design.**

In `_when_matches`, add a matcher that uses gitignore-style globs:

```python
import pathspec  # add to pyproject.toml install_requires

touch_tokens = [t for t in when if t.startswith("touches:")]
if touch_tokens:
    patterns = [t[len("touches:"):] for t in touch_tokens]
    spec = pathspec.PathSpec.from_lines(
        pathspec.patterns.GitWildMatchPattern, patterns,
    )
    key_files = task.get("key_files") or []
    matched = [kf for kf in key_files if spec.match_file(kf)]
    if matched:
        return True, f"touches=match:{matched[:3]}"
    return False, f"touches={patterns} not in key_files={key_files}"
```

OR semantics: any pattern matching any key_file passes. To get AND, declare multiple gates with one pattern each.

**Schema additions.** None (`when` already accepts free-form strings).

**Decisions made inline.**
- *Why `pathspec` and not stdlib `fnmatch`?* `fnmatch.fnmatch` does not interpret `**` recursively — it treats it as a single-component `*`. The example pattern `touches:**/auth/**` would silently fail to match nested files like `frontend/src/auth/Login.tsx`, which is the most common shape of this query. `pathspec` (used internally by Black, mypy, and many gitignore-aware tools) is MIT-licensed, has no transitive deps, and parses gitignore-style globs the way users expect (including `**`). It's a cheap, well-targeted dep.
- *Why match against `key_files` and not the actual git diff?* `key_files` is the contract the user already declares per task. Diff would be authoritative but requires running the implementer first; the matcher decides BEFORE implementation. Use the user's intent.
- *Why store at most 3 matched files in the reason string?* The reason is logged on every gate; long key-file lists pollute the log and the dashboard.

**General-purpose check.** No domain coupling.

**Effort.** **S** (1 day). Trivial. Test fixture for matching and non-matching cases.

### 2.18 Structured gate JSON output

**Verdict.** `gap-confirmed`. (Originally `out-of-scope` over schema-lock-in concerns; promoted to in-scope after risk-mitigation review made the lock-in trivially escapable.)

**Evidence.** `src/claude_plan_execute/gates/agent.py:79-86` — `passed = "verdict: pass" in (text or "").lower()` — the only structure the runner extracts from agent gates is the PASS/FAIL substring. Findings (security-auditor's category/severity/file/line, design-fidelity's viewport/finding-letter/selectors) live as freeform markdown. The §2.14 aggregation panel queries them via project-supplied regex over `<gate>.txt`, which is brittle to template changes.

**Rationale.** Adding a structured-findings appendix lets §2.14 query typed fields (severity, category, file) and lets the dashboard render trend graphs by category. The originally-blocking concern — once projects write aggregations against `findings_schema_v1`, evolving the schema is breaking — vanishes if the schema is permissive enough to let templates own their inner shape.

**Risk mitigation (the key design choice).** Three rules keep the build-tool source gate-agnostic:

1. **Permissive top-level schema.** Build-tool requires only that the appendix parses as JSON and normalizes to `{findings: list[dict]}`. Bare arrays wrap as `{findings: [...]}`. Anything weirder logs a warning and stores `{findings: [], _raw: <text>}`. **No required inner keys. No enum constraints. No type-checks beyond "is each finding a dict?".**
2. **Templates own their inner shape.** Per-template schemas are documented inline in the template prompt — `security-auditor.md` says "emit `{category, severity, file, line, evidence, suggested_fix}`"; `design-fidelity.md` says "emit `{finding_letter, viewport, selectors, risk}`". A future gate (project-supplied via `invariants.yaml`) emits whatever its template instructs. The build-tool source has zero coupling to specific finding shapes.
3. **Missing fields bucket as "(unknown)".** Aggregations against a field that's missing in some findings get an "(unknown)" bucket entry — no crash. Schema evolution path: a project adds `confidence: float` to its template; old runs lack the field; old aggregations bucket those as "(unknown)"; the project updates `aggregations.yaml` to query the new field. Build-tool source untouched.

**Design.**

Marker syntax in template output (HTML comments — invisible if rendered as markdown):

```
<!-- BEGIN_FINDINGS_JSON -->
[
  {"category": "ACL", "severity": "critical", "file": "src/api/works.py", "line": 142, "evidence": "..."},
  {"category": "Secrets", "severity": "high", "file": "src/config.py", "line": 88}
]
<!-- END_FINDINGS_JSON -->
```

Extraction in `gates/agent.py`:
1. After `run_claude` returns, regex-search the output for the marker pair (greedy multiline, first appendix only).
2. Absent → `findings=None`, no `.json` written. Existing v0.2.0 templates keep working.
3. Present → slice, `json.loads`, normalize per the rules above.
4. On `json.loads` failure → log warning, `findings=None`. **Don't fail the gate.** The text VERDICT remains the source of truth for pass/fail.

Storage:
- `task_dir/gates/<name>.txt` — unchanged (full response).
- NEW `task_dir/gates/<name>.json` — pretty-printed when extraction succeeds. Absent when no markers, parse fails, or gate is shell-kind.

`GateResult` enrichment: `findings: list[dict] | None = None` (frozen dataclass; preserve through `run_gates` re-construction).

**§2.14 aggregation panel update.** `aggregations.yaml` gains a `field:` (or `fields:` for composite) selector for JSON-mode queries; existing `extract:` regex mode stays for any-gate text queries. Mutually exclusive per entry. Loader rejects "both" or "neither" with a clear message.

**Decisions made inline.**
- *Why HTML comments not fenced code blocks?* Invisible in rendered markdown viewers (the agent's response is read as markdown by the dashboard); fenced JSON would render as a code block in dashboards that pretty-print. Comment-delimited keeps the appendix invisible-but-extractable.
- *Why first appendix only?* Multiple appendices invite ambiguity ("which one's authoritative?"). One-and-done is unambiguous.
- *Why don't shell gates produce `.json`?* Shell exit codes aren't structured findings. If a project really wants structured output from a shell gate, the script can write a sidecar JSON itself; the build-tool's appendix extraction is agent-gate-only.

**General-purpose check.** No domain coupling. Templates own their schemas; the build tool extracts whatever appears.

**Effort.** **S** (~30 min wall-clock based on v0.2.0 actuals). Build-order item 11.

### 2.21 Per-task `gates_extra` (new)

## 5. Pushback log

The owner's hypothesis list is more diligent than the average — half the items survive scrutiny. The four pushbacks below are the items I'd refuse to ship even if asked.

### Pushback 1 — §2.6 Gate-to-gate ordering DAG

The owner imagined "lint should arguably finish before design-fidelity bothers driving a browser." This is wrong on inspection: lint and design-fidelity test orthogonal contracts. Typecheck failure does not affect mobile-menu rendering — design-fidelity reads the running app, not the source.

The genuinely-needed ordering ("must finish before next") is `parallel_safe: false`. That covers the only real ordering concern: shared resources (the dev server). Layered DAG resolution would be 200+ lines of scheduler code for marginal token savings, and would multiply the bug surface. Don't ship.

### Pushback 2 — §2.13 Spec-coherence as its own gate kind

The owner imagined a `spec_coherence` gate kind taking a spec file and a coherence rule. This is the same shape as `untranslated-strings`: project supplies a script, runner runs it as a shell gate. The "rule" piece would either become a DSL (large surface, narrow win) or reduce to `bash -c`.

Adding a thin wrapper for what custom shell gates already do would be anti-DRY. The Bayān-shaped use case ("every route in §5 has a frontend file") is one Python script away from the existing `untranslated-strings` gate. **Document the recipe; don't ship a primitive.**

### Pushback 3 — §2.1 Custom gates as a parallel schema field

The owner imagined `tasks.yaml.custom_gates` as a new field. But `invariants.yaml` already does this. Adding a second mechanism for the same primitive creates two surfaces that drift; users get confused which to use; the build tool grows for no gain.

The fix is documentation: rename "invariants" in user-facing copy to "custom gates / invariants" so the discoverability matches the capability. Keep one mechanism.

### Pushback 4 — §2.5 Parallel task execution NOW

The owner's instinct is right that 50 sequential tasks leave wall-clock on the table. But a parallel scheduler without branch-per-task is a bug factory: parallel commits to a single branch race; the loser must rebase or lose work. Service contention multiplies. Rate-limit contention multiplies.

Build the prerequisites (branch-per-task, services, rate-limit retry) first. Then re-evaluate. By that point most slates will be running overnight regardless and the wall-clock gain is marginal. A `--continue-from FAILED` flag would buy more autonomy than concurrency. **Defer.**

### Honorable mention — §2.2 metric thresholds

Not a full pushback — just a reminder that `bash -c 'pytest --cov && coverage report --fail-under=80'` is already the right answer to "ensure value ≥ N." Don't ship a YAML primitive that's a thinner wrapper. The metric-history concern is dashboard work, not a gate primitive.
